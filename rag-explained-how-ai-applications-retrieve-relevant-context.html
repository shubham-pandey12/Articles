1. Why an LLM sometimes needs retrieval

A language model generates an answer from patterns learned during training and the context provided in its current request. That works well for many general tasks, but an application may need information that is private, frequently updated, or specific to a company.

Imagine a user asks: “What is our refund policy for annual subscriptions purchased through a reseller?” A general model cannot reliably know the company's current policy unless the relevant information is supplied. Guessing is dangerous: a fluent answer can still be wrong.

Retrieval-augmented generation (RAG) searches an external knowledge source and supplies relevant evidence to the model before it answers.

User question
↓
Retrieve relevant evidence
↓
Generate an answer grounded in that evidence

RAG does not automatically make answers correct. Retrieval can return the wrong passages, sources can be outdated, and the model can misread evidence. A reliable system needs both a retrieval pipeline and evaluation.

2. The complete RAG pipeline

A RAG system usually has two workflows: a background ingestion pipeline and an online question-answering pipeline.

Ingestion pipeline

Documents, web pages, database records
↓
Parse, clean, normalize text + metadata
↓
Split into chunks
↓
Generate embeddings
↓
Store text + vector + metadata + access rules
↓
Index for retrieval

Query pipeline

User question
↓
Validate identity and permissions
↓
Keyword + vector retrieval
↓
Filter, deduplicate, optionally rerank
↓
Select context within token budget
↓
LLM generates answer + citations

Ingestion can often run asynchronously in batches. Query retrieval needs to feel responsive. Keeping them separate makes it easier to reprocess documents without blocking live requests.

3. Start with the data, not the vector database

Before choosing a database, identify the sources, update frequency, access rules, content structure, authoritative sources, and deletion behavior. The ingestion pipeline should preserve metadata for citations, filtering, freshness, deduplication, debugging, and permission enforcement.

type DocumentChunk = {
  chunkId: string;
  documentId: string;
  title: string;
  text: string;
  sourceUrl?: string;
  sectionPath?: string[];
  updatedAt?: string;
  tenantId: string;
  allowedGroupIds: string[];
};

For documents containing tables, preserve row and column relationships where possible. Flattening a table can destroy the meaning of values. Scanned PDFs may need OCR, whose quality should also be monitored.

4. Chunking: choosing what the retriever can find

Embedding a large document as one vector is often not ideal: the user's question may refer to one paragraph while the vector represents several topics. Chunking splits content into smaller searchable units.

Fixed-size chunking

Advantages: simple, predictable, useful baseline. Limitations: can cut sentences, lists, or code examples in half and separate headings from explanations.

Structure-aware chunking

Split by headings, paragraphs, FAQ entries, or code blocks. It often keeps related ideas together and preserves section titles, but requires format-specific parsing and cleanup.

Overlap: useful, but not free

A small overlap can preserve context at boundaries. Too much creates near-duplicates, increases storage and embedding costs, and fills the prompt with repeated text. Test multiple chunking strategies against real questions.

Example: policy document

Chunk 1 · Direct annual purchases

Annual plans purchased directly from ExampleCo can be refunded within 14 days if usage is below the stated threshold.

Chunk 2 · Reseller purchases

Reseller purchases must be handled by the reseller. The customer should contact the reseller's billing team.

A reseller question can now retrieve the second chunk without bringing in the entire policy.

5. Embeddings: turning meaning into searchable vectors

An embedding model converts text into a numeric vector. Texts with similar semantic meaning often have vectors that are close under a chosen similarity measure. For example, “How do I reset my password?” and “I can't sign in—how can I change my credentials?” may point to the same help article even when wording differs.

Choose an embedding model based on quality on your domain, language support, input length, dimensions and storage cost, throughput, latency, price, licensing, and availability.

Model compatibility matters

Use compatible embedding models for indexed documents and queries. Changing models generally requires regenerating document embeddings and rebuilding or re-indexing the collection. Do not casually mix vectors from unrelated embedding spaces.

Embeddings are not a complete search system. Exact identifiers, product codes, error strings, and names may be better handled by lexical search.

Do not simply add raw vector similarity and BM25 scores unless they have been calibrated. Their scales can differ. Rank-based fusion or a trained reranker may be more appropriate.

7. Top-K retrieval is a trade-off

A retriever often returns the top K candidates. A small K can miss evidence; a large K adds noise, cost, latency, and context-window pressure. Tune K with a representative question set and verify whether the required evidence appears in results.

  • Recall: did retrieval find relevant evidence?
  • Precision: how much returned evidence is relevant?
  • Diversity: are results duplicates from one section?
  • Freshness: are results current?
  • Coverage: are all passages needed for a multi-part answer present?

Multi-hop questions may require query decomposition or iterative retrieval, but those techniques add complexity and latency. Establish a baseline first.

8. Reranking: improve the order of candidates

A reranker scores query–passage pairs more directly than a first-stage retriever. One common pattern is to retrieve dozens of candidates quickly, rerank them, then send only the strongest passages to the model.

Many candidate chunks
↓
Reranker scores query + each chunk
↓
A small set of relevant chunks
↓
LLM context

The numbers depend on the workload. Reranking can improve relevance but adds compute and latency; measure the trade-off for your data.

9. Metadata filtering and access control

Metadata can filter by product, document type, date, language, or tenant. It can also enforce access rules, but permissions must be designed carefully.

  1. Authenticate the user.
  2. Resolve permitted resources on the server.
  3. Apply access filters during retrieval.
  4. Re-check permissions before returning source details or full documents.
  5. Record useful audit events without leaking sensitive content into logs.
Filter before the prompt

Filtering after unauthorized chunks have been retrieved and passed to the model is too late. Access controls must apply before evidence enters model context.

Never let the model or a user-provided query freely choose the access-control filter. Derive it from trusted identity data.

10. Context construction: give the model evidence it can use

Context should include the question, relevant source passages, source identifiers or URLs, and a clear rule for missing evidence. Keep source boundaries visible.

SOURCE: refund-policy.md, section "Reseller purchases"
CONTENT:
Reseller purchases must be handled by the reseller.
The customer should contact the reseller's billing team.

USER QUESTION:
Who handles a refund for a reseller purchase?

Encourage the model to answer from evidence, avoid unsupported details, and admit when the context does not contain the answer. More text does not always improve accuracy; select for relevance, diversity, and token budget.

11. Citations: connect claims to their sources

Store source metadata with each chunk and preserve it through retrieval and generation. The UI can link a cited claim to the relevant document or section.

  • Retrieved source: a passage returned by search.
  • Cited source: a source the answer says it relies on.
  • Verified support: evidence that genuinely substantiates the claim.

A citation marker alone does not prove the claim is supported. Evaluate citation correctness and avoid generating links or source identifiers that did not come from the trusted retrieval layer.

12. What happens when retrieval finds nothing?

If passages are irrelevant, contradictory, or below a calibrated quality threshold, the assistant should not confidently invent an answer. It can ask a clarifying question, say the sources do not contain the answer, search another approved source, suggest a next step, or escalate to a human.

Similarity thresholds are not universal constants. Score distributions vary by model and dataset. Calibrate thresholds using real queries, including questions that have no answer in the corpus.

13. Freshness and document updates

Stale indexes produce stale answers. Plan for change detection, incremental reprocessing, removal of deleted documents, source versions and update times, duplicate prevention, ingestion retries, and visibility into index freshness.

For rapidly changing data such as order status, inventory, or account balance, a live API or database query may be better than a periodically refreshed document index. RAG is useful for knowledge; structured tools are often better for authoritative live state.

14. Evaluation: measure retrieval separately from generation

A polished answer can hide poor retrieval, so evaluate each stage separately.

Retrieval evaluation

  • Recall@K: how often relevant evidence appears in the top K results.
  • Precision@K: how many of the top K results are relevant.
  • MRR: how highly the first relevant result is ranked.
  • nDCG: whether results are ranked well when relevance has degrees.

Choose metrics that match the task. Finding all required passages can matter more than putting one relevant passage first.

Answer evaluation

Assess correctness against trusted sources, faithfulness, citation correctness, uncertainty, completeness, safety, latency, and cost. Maintain a fixed evaluation set when changing chunking, embeddings, retrieval settings, rerankers, or prompts. Include no-answer and adversarial cases.

15. A practical TypeScript pipeline

This example shows orchestration. Helper functions are illustrative application code, not built-in APIs.

type Evidence = {
  chunkId: string;
  text: string;
  sourceTitle: string;
  sourceUrl?: string;
};

async function answerQuestion(input: {
  question: string;
  userId: string;
  requestId: string;
}) {
  const access = await resolveKnowledgeAccess(input.userId);

  const [semanticResults, keywordResults] = await Promise.all([
    vectorSearch(input.question, { access }),
    keywordSearch(input.question, { access }),
  ]);

  const candidates = deduplicateAndFuse(
    semanticResults,
    keywordResults
  );

  const ranked = await rerank(input.question, candidates);
  const evidence: Evidence[] = selectEvidenceWithinBudget(ranked, {
    maxChunks: 8,
    maxTokens: 5000,
  });

  if (evidence.length === 0) {
    return {
      answer: "I couldn't find enough information in the available sources.",
      citations: [],
    };
  }

  const result = await generateGroundedAnswer({
    question: input.question,
    evidence,
    requestId: input.requestId,
  });

  return {
    answer: result.answer,
    citations: validateCitations(result.citations, evidence),
  };
}

Production code also needs provider errors, timeouts, cancellation, retries, redacted logs, schema validation, freshness rules, and full permission checks. The access object must come from trusted server-side identity data.

16. Common RAG mistakes

  1. Choosing a vector database before understanding the data. Ingestion quality and metadata may matter more than the brand.
  2. Using arbitrary chunk sizes. Compare strategies with real questions.
  3. Using vector search for everything. Exact identifiers often benefit from lexical search.
  4. Sending every chunk to the model. Select relevant evidence within a context budget.
  5. Ignoring access control. Filter before content enters model context.
  6. Assuming a citation proves correctness. Verify that it supports the claim.
  7. Never updating the index. Deleted and superseded documents must stop appearing.
  8. Evaluating only final answers. Track retrieval failures separately.
  9. Treating RAG as a live database. Query authoritative systems for real-time state.
  10. Assuming RAG prevents hallucinations. It helps ground answers but cannot guarantee correctness.

17. A sensible implementation plan

  1. Define the corpus, ownership, permissions, and freshness requirements.
  2. Build ingestion: parse, clean, chunk, store metadata, and handle updates/deletions.
  3. Create a small evaluation set with realistic questions and relevant source passages.
  4. Implement baseline retrieval with vector or keyword search, based on the data.
  5. Add hybrid search if it improves evidence recall.
  6. Tune chunking and top K using evaluation results.
  7. Add reranking only if its improvement justifies the latency and cost.
  8. Generate grounded answers with citations and no-evidence behavior.
  9. Test access controls, including cross-user and cross-tenant cases.
  10. Monitor ingestion failures, retrieval metrics, answer quality, latency, and cost.

Final checklist

  • Documents are parsed correctly and have useful metadata.
  • Chunking preserves important structure.
  • Query and document embeddings use compatible models.
  • Keyword search handles exact terms where needed.
  • Results are deduplicated and fit the context budget.
  • Access filters come from trusted identity data.
  • The model distinguishes evidence from uncertainty.
  • Citations map to trusted sources and are validated.
  • No-answer and conflicting-source cases are handled.
  • Index updates and deletions are reliable.
  • Retrieval and answer quality are evaluated separately.
  • Latency, cost, freshness, and failures are observable.

Conclusion

RAG is not simply “put documents in a vector database and ask an LLM.” It is a complete data and retrieval pipeline: parsing, chunking, indexing, searching, filtering, ranking, context construction, generation, citations, and evaluation.

Start with the knowledge sources and the questions users actually ask. Build a measurable baseline, preserve permissions and source metadata throughout the pipeline, and add complexity only when it improves retrieval or answer quality.

The goal is not to retrieve the most text. It is to retrieve the right evidence and help the model use it correctly.
