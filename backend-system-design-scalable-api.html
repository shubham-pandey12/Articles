Backend System Design: Designing a Scalable API from Requirements to Deployment

Turn vague product requirements into an API architecture that can handle real traffic, data consistency, failures, and future change—without adding complexity before it is needed.

Who this is for

Frontend and backend developers preparing for system design interviews or building production APIs with Node.js, TypeScript, and a relational database.

Core idea: design from requirements. Every component should solve a clear problem, and every important failure mode should have an intentional response.

1. What backend system design actually means

Backend system design is the process of deciding how a service behaves, how its parts communicate, where data lives, and how the system handles growth and failure. It is not just choosing Node.js, PostgreSQL, Redis, or a cloud provider. Those are implementation choices; first, understand the problem and constraints.

A useful design explains what the system must do, the traffic and data it must support, the consistency each operation needs, what happens when a dependency fails, and how the team deploys and observes it.

Rule of thumb: choose the simplest design that meets the requirements for reliability, performance, cost, and operational effort.

2. Start with requirements, not boxes and arrows

Imagine a deal-booking platform. Customers browse deals, create bookings, and check booking status.

Functional requirements

  • Browse and search available deals.
  • View deal details and availability.
  • Create a booking and read its status.
  • Notify a customer when the booking changes.

Non-functional requirements

  • Latency: common reads should meet an agreed target.
  • Availability: browsing should survive a notification-provider outage.
  • Consistency: customers must not reserve the same final inventory unit.
  • Durability: confirmed bookings survive process restarts.
  • Security: customers can read only their own bookings.
  • Scalability: capacity can be added where measurements show a need.

Agree on measurable targets with product and engineering. Example latency targets are planning inputs, not universal standards.

Estimate scale

Suppose 100,000 active users make 20 API requests each per day: 2,000,000 requests daily.

2,000,000 / 86,400 ≈ 23 requests/second average
Peak at 10× average ≈ 230 requests/second

Also estimate the read/write ratio, payload sizes, data growth, concurrent requests, job volume, and retention needs. Traffic is uneven, so average rate alone is not enough.

3. Define the API contract

MethodEndpointPurpose
GET/v1/dealsList and filter deals
GET/v1/deals/:idRead one deal
POST/v1/bookingsCreate a booking
GET/v1/bookings/:idRead booking status
POST /v1/bookings
Authorization: Bearer <token>
Idempotency-Key: 2cc9d8...
Content-Type: application/json

{
  "dealId": "deal_123",
  "quantity": 1
}

Specify required fields, validation limits, authentication, authorization, errors, pagination, idempotency, and compatibility. Use status codes intentionally: 201 for creation, 400 for invalid input, 401 for invalid authentication, 403 for insufficient permission, 409 for state conflicts, and 429 for rate limiting. Never expose stack traces or raw database errors.

4. A sensible first architecture

For many product APIs, a modular monolith is a better starting point than immediately splitting the system into microservices.

Web / Mobile Client
↓
Load Balancer / API Gateway
↓
Backend API instances
↓
Relational database
Durable source of truth
Optional cache
Faster repeated reads
Queue → Workers
Slow background tasks
  • Load balancer: distributes requests across healthy instances.
  • API: validates requests and runs business rules.
  • Database: stores authoritative data.
  • Cache: reduces repeated reads when staleness is acceptable.
  • Queue: moves slow or retryable work out of the response path.

Do not add Redis, Kafka, Kubernetes, or a service mesh just because they make a diagram look advanced.

Routes/controllers map HTTP to application calls. Validators reject malformed input. Services enforce business rules. Repositories contain persistence logic. Workers handle asynchronous jobs. Avoid both giant controllers and layers of abstractions that do not clarify responsibility.

6. Follow one request through the system

For POST /v1/bookings, a robust flow is:

  1. Apply request-size and rate limits.
  2. Authenticate the caller and validate the body.
  3. Check the idempotency key.
  4. Begin a database transaction.
  5. Reserve inventory atomically and create the booking.
  6. Store the idempotency result and an outbox event within the transaction where feasible.
  7. Commit and return the booking.
  8. Let a worker deliver the notification asynchronously.
The transactional outbox helps avoid the gap where a booking commits successfully but the process crashes before publishing its notification event.

7. Protect data integrity under concurrency

Two requests can both read an inventory count of one before either updates it. An application-level “read, check, decrement” sequence can oversell inventory.

Use atomic conditional updates, row-level locks, constraints, and correctly scoped transactions. For example:

UPDATE deal_inventory
SET available_quantity = available_quantity - 1
WHERE deal_id = $1
  AND available_quantity >= 1
RETURNING available_quantity;

If no row is returned, the reservation was not made. The complete booking operation still needs transaction boundaries and correct error handling. Critical invariants should be enforced by the database wherever possible.

8. Make retries safe with idempotency

A client may send a booking request, the server may commit it, and the response may be lost. A retry should not create a second booking.

  1. Scope the idempotency key to the authenticated customer and operation.
  2. Store a request hash so the same key cannot represent a different payload.
  3. Coordinate concurrent requests with a unique constraint or equivalent lock.
  4. Persist the result so a valid retry can replay it.
  5. Define a retention period and cleanup strategy.

Idempotency does not mean the network executes an operation exactly once. It makes repeated requests produce one logical effect.

9. Scale stateless API instances horizontally

Client→Load balancer→API A / B / C→Shared database

Keep shared state in shared systems rather than one process's memory when it must work across instances. Watch connection pool sizes and concurrency limits: adding API servers can overload the database if each server opens too many connections. Measure database and downstream saturation before scaling the application tier.

10. Cache reads carefully

A cache-aside flow checks the cache, reads the database on a miss, stores the result with a suitable TTL, and returns it. The hard part is invalidation and correctness.

  • How stale can the data be?
  • Which writes invalidate or update it?
  • What happens if the cache is down?
  • Can many simultaneous misses overload the database?
  • Are keys scoped by tenant, user, locale, and permissions?

Never cache permission-sensitive responses under a shared key. For inventory and booking decisions, keep the database authoritative unless a different consistency model is explicitly designed.

11. Move slow work to a queue

API→Database + outbox→Queue→Worker→Provider

Email, reports, and image processing often belong in background jobs. Use bounded retries with backoff and jitter, processing deadlines, idempotent handlers, dead-letter inspection, and queue-age monitoring. Queues commonly deliver at least once, so consumers must tolerate duplicate jobs.

12. Set timeouts and limit failure propagation

Every network call needs a timeout. A good policy defines a total request deadline, shorter per-dependency timeouts, bounded retries for safe operations, exponential backoff with jitter, and cancellation when the caller disconnects where supported.

Do not retry validation errors. Do not blindly retry non-idempotent payments or bookings. If a notification provider fails, the booking may still succeed and the notification can be retried. If inventory cannot be checked reliably, confirming a booking may be unsafe. Failure behavior must follow business requirements.

13. Design observability before production

Metrics

  • Request rate, error rate, and latency percentiles such as p95 and p99.
  • Database query latency and connection pool saturation.
  • Cache hit ratio and queue depth/oldest job age.

Logs

Use structured logs with request or trace IDs, route template, status, duration, and error category. Never log passwords, access tokens, payment secrets, or unnecessary personal data.

Traces

Trace time spent in the API, database, cache, queue, and downstream services. Alert on sustained user-visible failures and saturation rather than every isolated exception.

14. Secure every boundary

  • Authenticate and authorize every resource operation.
  • Validate input and use parameterized database queries.
  • Enforce tenant isolation consistently.
  • Apply rate limits and payload-size limits.
  • Manage secrets securely and use TLS.
  • Restrict CORS to intended browser origins.
  • Avoid leaking internal errors; audit sensitive administrative actions.
  • Keep dependencies patched and scan build artifacts.

A valid token does not grant access to every record. A booking read must check whether the caller is allowed to see that booking.

15. Scale the database in the right order

Before sharding, investigate missing indexes, N+1 queries, overly broad selects, slow plans with EXPLAIN ANALYZE, long transactions, lock contention, excessive connections, and expensive offset pagination.

Then consider read replicas, partitioning, or sharding when the workload justifies the added complexity. Replicas may lag behind the primary, so a read-after-write request should not go to a lagging replica if immediate visibility is required.

16. Deploy without stopping the world

  1. Run linting, type checks, and unit tests.
  2. Run integration tests against realistic dependencies.
  3. Build an immutable artifact or container image.
  4. Run security checks and deploy to a test environment.
  5. Run smoke tests, then gradually roll out.
  6. Monitor and define rollback criteria.

Use expand-and-contract database migrations: add a backward-compatible schema change, deploy compatible code, backfill data, switch reads and writes, then remove old schema after old code is gone. Readiness checks prevent traffic from reaching unready instances. Graceful shutdown stops new requests and gives in-flight work a bounded time to finish.

17. Worked example: a booking API

Initial design

  • Node.js/TypeScript modular API.
  • PostgreSQL as source of truth for deals, inventory, bookings, and idempotency records.
  • Optional Redis cache for public deal details after measurement.
  • Transactional outbox plus worker for notifications.
  • Centralized logs, metrics, traces, and alerts.

Critical write path

Authenticate + validate
↓
Claim idempotency key
↓
Transaction: reserve inventory + booking + outbox
↓
Commit → return booking
↓
Worker delivers notification with safe retries

Test the failure cases

  • Two concurrent requests for one remaining unit.
  • Same idempotency key repeated; same key with different payload.
  • Database timeout during booking.
  • Worker crashes after sending but before acknowledging a job.
  • Notification provider outage.
  • Deployment while requests are in flight.

The architecture is useful because each component has a specific responsibility tied to a requirement.

18. Common system-design mistakes

  • Starting with microservices before defining boundaries.
  • Choosing technologies before estimating load and consistency needs.
  • Treating cached data as the source of truth for critical writes.
  • Ignoring duplicate requests and concurrent updates.
  • Retrying unsafe operations without protection.
  • Putting slow external calls on every critical request path.
  • Having no timeouts, backpressure, or graceful shutdown.
  • Scaling API instances while ignoring database saturation.
  • Claiming “exactly once” delivery without explaining actual guarantees.

19. System-design interview checklist

  1. Clarify functional requirements and out-of-scope behavior.
  2. Set measurable latency, availability, consistency, and security goals.
  3. Estimate request rate, peak load, and data growth.
  4. Define resource-oriented API contracts.
  5. Draw the simplest viable architecture.
  6. Walk through a read path and a critical write path.
  7. Explain schema, constraints, and transaction boundaries.
  8. Discuss idempotency, concurrency, and failure handling.
  9. Add caching and background processing only where justified.
  10. Cover authentication, authorization, and tenant isolation.
  11. Explain observability, deployment, migrations, and rollback.
  12. Identify bottlenecks and how to validate them with tests and measurements.
Final thought: a strong system-design answer is not a list of fashionable tools. It connects each requirement to a design choice, explains trade-offs, and plans for important failure modes.
