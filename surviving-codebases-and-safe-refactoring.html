Working in an Existing Codebase: Refactoring Safely Without Breaking Everything

A practical guide to understanding unfamiliar projects, reducing risky coupling, and shipping maintainable changes.

Most professional development is not greenfield work. You inherit a repository with unfamiliar conventions, shared components, old dependencies, hidden assumptions, and a deadline. The job is to make the requested change while keeping the rest of the system stable.

1. Understand the system before editing

Start with the smallest set of files that explains the user journey. Read the README, package scripts, environment-variable examples, application entry point, routing, test setup, and CI workflow. Run the app and tests before changing anything so you know whether a failure already existed.

Map:
- Where does the request enter the system?
- Which component or route owns the user interaction?
- Where is business logic implemented?
- How does data move through API clients, services, and persistence?
- What tests and monitoring cover this behavior?
- Which other pages reuse the component you plan to change?

Do not start by reorganizing the entire folder structure. First learn the local conventions and establish a working baseline.

2. Trace one real user journey end to end

For a feature such as “save a supplier configuration,” follow the path from click to persisted result:

Button click
  → form validation
  → mutation hook
  → API client
  → backend route/controller
  → service/business rules
  → repository/database
  → response mapping
  → cache update / UI feedback

At each boundary, note the input, output, error behavior, and owner. This exposes duplicate validation, hidden side effects, and unclear responsibilities. Use IDE “find references” and call hierarchy tools instead of guessing where a function is used.

3. Refactor in small, behavior-preserving steps

Refactoring changes internal structure without intentionally changing external behavior. The safest sequence is:
1. Add or identify tests for current behavior.
2. Make one small structural change.
3. Run targeted tests and inspect the diff.
4. Repeat.
5. Keep the change easy to review and revert.

For example, extract a repeated card into a shared component only after identifying which props and states genuinely vary. Avoid creating a giant “universal component” with dozens of optional props. A reusable component should have a clear contract and a small number of meaningful variants.

4. Find the right component boundary

A component is a good candidate for extraction when it has a coherent responsibility, is repeated, or makes a parent difficult to understand. Separate:
- UI primitives: buttons, inputs, cards, dialogs, layout containers.
- Feature components: supplier selector, deal card, checkout summary.
- Page composition: data loading and orchestration for a route.
- Domain logic: rules that can often be tested without rendering UI.

Do not extract every three-line fragment. Abstraction has a cost: extra files, indirection, props, and concepts future developers must learn. Reuse is valuable when it makes change safer, not merely when two snippets look similar.

5. Separate responsibilities without overengineering

A common frontend shape is pages/ for route-level composition, features/ for user capabilities, components/ui/ for stable primitives, services/ for network access, and hooks/ for reusable React behavior. A backend might organize code by feature, with controllers, services, repositories, schemas, and tests.

These are options, not universal laws. A small project does not need a complex enterprise architecture. Prefer feature ownership and explicit boundaries over splitting every function into a separate file. Keep business rules out of visual components when those rules need reuse or independent testing.

6. Make shared changes with blast radius in mind

A shared button or API client can affect many pages. Before changing it, search all call sites and classify them: default usage, custom variants, disabled/loading behavior, accessibility requirements, and unusual edge cases. Add a test for the contract and consider a gradual migration.

A useful practice is to search for the component name, inspect props passed at each call site, and run tests for the most important consumers. If the component is widely used, avoid silently changing a default that other pages depend on. Introduce a new explicit prop or variant when compatibility matters.

7. Refactor API and data boundaries carefully

Do not let each component build slightly different URLs, duplicate authentication headers, and interpret errors differently. A shared API client can centralize base URL, timeouts, serialization, and error normalization. Feature-level services can express operations such as getSupplierConfig or updateSupplierConfig.

Keep validation on the server even if the UI validates too. UI validation improves experience; server validation protects the system. When changing response shapes, search consumers, add compatibility if needed, and coordinate frontend/backend deployments so neither side temporarily expects a field the other side does not provide.

8. Reduce risk with feature flags and incremental rollout

A feature flag can separate deployment from release: code can reach production while the new behavior remains disabled. Use flags for risky changes when the platform supports them, define who can enable the flag, and decide when it will be removed.

For a database migration, prefer expand-and-contract:
1. Add the new field or table in a backward-compatible way.
2. Deploy code that can read/write safely during transition.
3. Backfill data and verify it.
4. Switch reads to the new shape.
5. Remove the old structure only after all consumers have migrated.

Never assume a rollback is safe after an irreversible data migration. Plan how old and new application versions coexist.

9. Tests as a safety net, not a checkbox

A useful test suite checks externally meaningful behavior. Test a shared component's public contract, feature-level logic, API/database boundaries, and critical end-to-end journeys. Include empty, loading, error, permission, and boundary states where relevant.

When refactoring, a failing test can reveal that the code relied on a hidden behavior. Do not immediately rewrite the test to make it pass. First decide whether the old behavior was intentional, accidental, or undocumented. Keep tests deterministic by controlling time, randomness, network calls, and external dependencies.

10. Use static analysis and repository tools

Run the checks the repository actually defines, such as:

npm ci
npm run lint
npm run typecheck
npm test
npm run build

Not every project has all these scripts. Read package.json rather than assuming names. Formatters, type checkers, linters, and dependency scanners catch different classes of mistakes. They do not replace code review, runtime testing, or understanding the business requirement.

Before a PR, inspect git diff, check for debug logs and secrets, and make sure generated files and local environment files are not accidentally included.

11. How to handle legacy code that has no tests

Do not rewrite the whole module because it is hard to understand. First write characterization tests around observable behavior. These tests document what the current system does, even if some behavior looks odd. Then extract a small pure function or wrap a dependency so it can be tested.

When tests are impossible at first, use a small manual verification matrix, logs, feature flags, and narrow changes. Capture the baseline before changing behavior. If you discover a bug while refactoring, separate the behavior fix from the structural refactor when possible so reviewers can reason about each change independently.

12. Review your own pull request

Pretend you are a teammate seeing the change for the first time. Ask:
- Does the diff solve the stated problem and nothing unrelated?
- Are names and abstractions understandable?
- Did I change public behavior, API contracts, defaults, or error handling?
- Are edge cases and permission checks covered?
- Are loading, empty, and error states handled?
- Did I add tests that would catch a regression?
- Can this deploy alongside the current backend and database?
- Is there a safe rollback or mitigation?

Write the PR description as a short explanation of the problem, solution, tests, and risk. A small, clear PR is often safer and faster to ship than a large “cleanup” PR.

13. Common traps

  • Renaming or moving many files while also implementing a feature.
  • Abstracting based only on visual similarity.
  • Hiding business rules inside UI code or generic utility functions.
  • Replacing working code with a new library without measuring the benefit.
  • Changing API response contracts without finding every consumer.
  • Deleting “unused” code before verifying dynamic imports or runtime references.
  • Treating passing unit tests as proof that integration behavior is unchanged.
  • Making a refactor too large to review or roll back.

The best architecture is not the one with the most folders. It is the one that helps the next engineer understand where a change belongs and what it might affect.

14. A safe-change checklist

Before: understand the journey, run the baseline, search call sites, identify public contracts, and define expected behavior.

During: change one boundary at a time, keep names explicit, add characterization or regression tests, and avoid unrelated formatting or file moves.

Before merge: run the repository's checks, inspect the final diff, check secrets and logs, document compatibility risks, and ask for focused review.

After merge: verify the behavior in the deployed environment, monitor errors, remove temporary flags when safe, and document any surprising dependency you discovered.

Final takeaways

When working in an unfamiliar codebase, first understand the behavior and boundaries. Then make the smallest safe change, test the contract, inspect the blast radius, and keep the pull request reviewable. Maintainability comes from clear responsibilities and predictable change—not from abstraction for its own sake.
