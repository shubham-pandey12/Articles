Unit, Integration, and E2E Testing: What Should You Test?

A practical guide to choosing the right test level, testing user-visible behavior, and building confidence without creating a slow or brittle test suite.

1. Testing is about confidence, not test count

A test suite is useful when it helps a team change software without accidentally breaking important behavior. Hundreds of tests do not automatically mean an application is well tested. Tests may repeat low-value checks, assert implementation details, or fail whenever a harmless refactor changes internal structure.

Ask this instead

What could break, how would we notice, and what is the cheapest reliable way to detect it?

For a product search page, you might test a price formatter, verify that a filter updates results, check the error state after an API failure, and protect the full journey from search to cart. These are different behaviors, so they deserve different strategies.

2. The three main levels

E2E tests Complete user journeys
Integration tests Components + state + APIs
Unit tests Small, isolated behavior

Unit tests

Test a small unit of logic in isolation, such as a formatter, validator, or calculation. They are usually fast and help pinpoint a failure.

Integration tests

Test whether multiple pieces work together. For frontend applications, this might mean rendering a form, entering values, submitting it, and checking the visible result while mocking the network boundary.

End-to-end (E2E) tests

Drive the application through a real browser or browser-like environment and verify complete user journeys. They can catch routing, integration, and configuration problems, but are typically slower and need more maintenance.

There is no universal ratio that every project must follow. The right mix depends on risk, architecture, and how expensive each test is to maintain.

3. Unit tests: test logic that can fail independently

Unit tests are a good fit for deterministic logic with meaningful input/output behavior: formatting, calculations, validation, sorting, data mapping, and permission decisions.

export function calculateTotal(
  price: number,
  quantity: number,
  discountPercent = 0
) {
  if (price < 0 || quantity < 0) {
    throw new Error("Price and quantity must be non-negative");
  }

  const subtotal = price * quantity;
  return subtotal * (1 - discountPercent / 100);
}
import { describe, expect, it } from "vitest";
import { calculateTotal } from "./calculateTotal";

describe("calculateTotal", () => {
  it("calculates a total with a discount", () => {
    expect(calculateTotal(100, 2, 10)).toBe(180);
  });

  it("returns zero for zero quantity", () => {
    expect(calculateTotal(100, 0)).toBe(0);
  });

  it("rejects negative quantities", () => {
    expect(() => calculateTotal(100, -1)).toThrow();
  });
});

This covers a normal case, a boundary case, and invalid input. Tests should cover meaningful behavior, not just typical examples.

When not to write a unit test

A test for a trivial wrapper may add little value if it only repeats the implementation. Testing every private helper can make refactoring unnecessarily painful. Focus on behavior that matters and logic with meaningful risk.

4. Integration tests: verify behavior across boundaries

Many frontend bugs occur between components, state, routing, and data. A filter might render correctly by itself but fail when connected to query parameters or fetched results.

import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { describe, expect, it, vi } from "vitest";
import { SearchForm } from "./SearchForm";

describe("SearchForm", () => {
  it("submits the entered search term", async () => {
    const user = userEvent.setup();
    const onSearch = vi.fn();

    render(<SearchForm onSearch={onSearch} />);

    await user.type(
      screen.getByRole("textbox", { name: /search products/i }),
      "keyboard"
    );
    await user.click(
      screen.getByRole("button", { name: /search/i })
    );

    expect(onSearch).toHaveBeenCalledWith("keyboard");
  });
});

This test focuses on what a user does and what the application reports, not internal state variable names.

Should integration tests mock the API?

Often, yes. Mocking at the network boundary makes tests repeatable and lets you simulate success, empty results, slow responses, and errors. Keep mock responses close to the real API contract. Tools such as Mock Service Worker (MSW) can intercept network requests without changing production code paths.

5. E2E tests: protect critical user journeys

E2E tests run through a real application flow, usually in a browser. They help check that routing, browser events, frontend bundles, backend integration, and critical business behavior work together.

  1. Open the product listing.
  2. Search for an item.
  3. Open its details.
  4. Add it to the cart.
  5. Enter valid checkout information.
  6. Submit the order.
  7. Verify the confirmation page.
import { test, expect } from "@playwright/test";

test("customer can add a product to the cart", async ({ page }) => {
  await page.goto("/products");

  await page.getByRole("searchbox", { name: /search products/i })
    .fill("keyboard");
  await page.getByRole("button", { name: /search/i }).click();

  await page.getByRole("link", { name: /mechanical keyboard/i }).click();
  await page.getByRole("button", { name: /add to cart/i }).click();

  await expect(page.getByRole("status"))
    .toContainText(/added to cart/i);
});

Exact selectors and routes depend on the application. Prefer accessible roles and labels because they are meaningful to users and less coupled to CSS implementation.

Do not turn E2E into a giant suite. Browser tests can be slow and fail due to environment or test data. Test detailed calculations and edge cases at lower levels; use E2E for journeys whose failure would seriously affect users.

6. A practical example: testing a login form

Suppose a login form has email and password fields, a submit button, validation, and an API request.

BehaviorSuggested levelWhy
Email validation ruleUnitPure logic with many input cases
Password-required ruleUnitSmall deterministic rule
Error after invalid submissionIntegrationChecks form and validation UI
Successful submit calls auth API and navigatesIntegrationVerifies form and network boundary
User signs in and reaches dashboardE2EProtects the full critical journey
Session expiry redirects to sign-inIntegration or E2EChoose based on where the risk lies

The same feature may need multiple test levels, but each test should cover a distinct risk rather than duplicate the exact same assertion.

7. Test user-visible behavior, not implementation details

Brittle tests ask how a component is implemented: whether an internal function was called, whether a state variable has a particular name, or whether a CSS class exists. Sometimes implementation assertions are appropriate, but frontend tests are usually more robust when they focus on behavior.

  • Can the user find and operate the control?
  • Does the right message appear?
  • Does the correct result show after submission?
  • Is the button disabled when submission is invalid?
  • Does the user receive feedback when the request fails?

Prefer getByRole, getByLabelText, and getByText over selectors tied to internal class names.

8. Cover states, not just the happy path

StateWhat to verify
LoadingA clear loading indicator is present
SuccessExpected rows and values appear
EmptyA helpful empty state appears
ErrorAn error message and recovery option appear
FilteringResults match the selected filter
PaginationThe next page shows the correct data
Permission deniedRestricted actions are not offered; server still enforces access
Slow requestThe UI behaves as intended while waiting

Not every state needs a separate E2E test. Most can be covered by component or integration tests, with a few critical flows protected in the browser.

9. Async behavior, timers, and race conditions

Tests should wait for the expected result instead of relying on arbitrary sleeps.

// Avoid arbitrary waits
await new Promise((resolve) => setTimeout(resolve, 1000));

// Prefer condition-based assertions
expect(
  await screen.findByText(/results loaded/i)
).toBeInTheDocument();

For debounce logic, use fake timers in unit tests when appropriate. For request races, test a scenario where a user changes the search term quickly and ensure stale results do not overwrite newer ones. Use controlled promises or network handlers rather than random delays.

10. Mock carefully

Good reasons to mock include third-party services you do not control, network outcomes that need to be deterministic, time, randomness, or browser APIs that are difficult to control.

Be cautious about mocking the component's own business logic, every hook, the entire data layer in a test meant to validate data integration, or backend response shapes without a contract. Mock at the boundary of the behavior under test. If a test is about how a form responds to an API error, mock the HTTP response and let the real form logic run.

11. Accessibility testing belongs in normal tests

Accessibility is part of functionality. Include checks that inputs have labels, buttons have meaningful accessible names, dialogs manage focus, errors are associated with fields, keyboard users can operate key flows, and status updates are announced appropriately.

Accessible selectors improve tests too. A query using getByRole("button", { name: /save/i }) checks that the button has a useful accessible name, not just that a DOM node exists. Automated tools catch some issues, but do not replace keyboard and screen-reader testing for important journeys.

12. Where each test level fits in CI

Pull request
↓
Lint + TypeScript
↓
Unit tests
↓
Component / integration tests
↓
Build + bundle checks
↓
Critical E2E / smoke tests
↓
Deploy + post-deploy checks

The exact order varies. Unit and integration tests may run in parallel. E2E tests may run on every pull request or in a dedicated pre-release pipeline. Optimize for quick feedback without skipping high-risk coverage. Preserve traces or screenshots when useful and keep test data reproducible.

13. Common testing mistakes

  1. Testing only the happy path. Include important invalid, empty, and error states.
  2. Testing every detail at E2E level. Browser tests are more expensive and harder to diagnose.
  3. Asserting internal implementation. Refactors should not break tests if behavior remains the same.
  4. Using arbitrary timeouts. Wait for meaningful conditions.
  5. Over-mocking. A test can pass while the real integration is broken.
  6. Sharing mutable test data. Tests can become order-dependent and flaky.
  7. Ignoring accessibility. A visually correct control may still be unusable.
  8. Measuring quality by test count or coverage alone. Coverage does not prove meaningful behavior is protected.
  9. Keeping flaky tests without ownership. Flaky tests reduce trust.

14. How to choose what to test

  1. Is it deterministic logic with inputs and outputs? Start with a unit test.
  2. Does it depend on multiple components, state, routing, or network handling? Use an integration test.
  3. Must you verify the complete browser journey across deployment and backend boundaries? Add an E2E test.
  4. Is the behavior business-critical, security-sensitive, or costly to break? Increase coverage at the most useful levels.
  5. Does a test duplicate another without catching a distinct failure? Simplify or remove the duplication.

Consider failure impact and likelihood. A currency calculation may deserve strong unit coverage. Sign-in or checkout may deserve a few E2E checks. A decorative tooltip may need only a focused component test—or no dedicated test if risk is low.

15. A practical test plan for a React feature

  • Unit: query normalization, sorting, formatting, filter calculations.
  • Integration: query submission, loading results, empty/error states, pagination, retry.
  • E2E: search for a product, open details, add to cart.
  • Accessibility: label and role checks, keyboard navigation for key interactions.
  • Performance/observability: monitor slow API calls and route performance outside ordinary functional assertions.

This is not a fixed formula. Adjust it to the feature's risk and the cost of maintaining each test.

16. Final checklist

  • Tests protect behavior that matters to users or the business.
  • Pure logic is tested at unit level where useful.
  • Components and data interactions are tested together.
  • A small set of critical journeys is covered end to end.
  • Loading, empty, error, validation, and permission states are considered.
  • Tests use accessible queries and meaningful assertions.
  • Network mocks reflect the real API contract.
  • Async tests wait for conditions rather than arbitrary delays.
  • Test data is isolated and repeatable.
  • Failures are actionable and flaky tests are fixed promptly.
  • Coverage is a signal, not the sole measure of quality.

Conclusion

Unit, integration, and E2E tests are complementary tools. Unit tests help you trust individual rules. Integration tests help you trust how frontend pieces work together. E2E tests help you trust the critical journeys users depend on.

Do not chase a perfect test pyramid or a universal coverage percentage. Identify important failure modes, test them at the cheapest reliable level, and keep the suite stable enough that developers trust its feedback.

A good test suite is not the one that tests the most code. It is the one that catches meaningful regressions quickly and makes safe change easier.
