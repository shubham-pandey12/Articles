Git is the tool that records changes on your computer. GitHub is a place to store Git repositories online and collaborate with other developers. In daily work, the goal is not to memorize every command. It is to understand what state your code is in, what you want to change, and how to recover safely when something goes wrong.

1. The mental model: Git vs GitHub

Think of your project as a folder with a history. Git records snapshots of changes. GitHub hosts that history and adds collaboration features such as pull requests, reviews, issues, Actions, releases, and project permissions.

A useful mental model:
- Working tree: files you are currently editing.
- Staging area: the changes you selected for the next snapshot.
- Commit: a named snapshot of selected changes.
- Branch: a separate line of work.
- Remote: a repository hosted somewhere else, often GitHub.
- Pull request (PR): a proposal to merge one branch into another after discussion and review.

Git does not automatically know which changes are safe to publish. You choose what to stage and commit.

```text Edit files → Stage selected changes → Commit snapshot ↑ ↓ Working tree Local history ↕ push / pull GitHub remote ↓ Pull request → Review → Merge ```

2. Set up your identity and repository

Set your name and email once on a machine. Use the email you want associated with commits; for work, follow your company's account policy.

git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --list

Create a repository locally with git init, or copy an existing remote repository with git clone. Cloning downloads the project and configures a remote usually named origin.

git init
git clone https://github.com/OWNER/REPOSITORY.git
cd REPOSITORY
git remote -v

3. The daily workflow you will use most

Before changing code, check where you are and whether you have uncommitted work.

git status
git branch --show-current
git pull --rebase origin main

Create a focused branch, make a small change, inspect it, stage only what belongs together, then commit.

git switch -c fix/search-empty-state
# edit files
git diff
git status
git add src/search/EmptyState.tsx
git diff --staged
git commit -m "Fix empty search state"
git push -u origin fix/search-empty-state

git diff shows unstaged changes. git diff --staged shows what will go into the commit. git add does not upload anything; it only selects content for the next commit. git push sends your local commits to the remote.

Prefer commits that represent one logical change. A bug fix and a drive-by formatting change are usually easier to review separately.

4. Read status and history before guessing

When something looks wrong, gather information before running a destructive command.

git status --short
git log --oneline --graph --decorate -15
git show --stat HEAD
git diff
git diff --staged
git branch -vv
git remote -v

These answer common questions: Which files changed? What was the last commit? Which branch am I on? Is my branch tracking a remote branch? What exactly am I about to commit? The --graph view makes branch merges easier to understand.

5. Branching, switching, and keeping work separate

A branch is a movable name pointing to a commit. It lets you work on a feature or fix without immediately changing main.

git switch -c feature/profile-settings
git switch main
git branch
git branch -d feature/profile-settings

Use git switch for changing branches and git restore for restoring file content; these modern commands are easier to understand than older overloaded commands. Do not delete a branch until you are sure its work is merged or otherwise saved.

6. Pull, fetch, merge, and rebase in plain English

  • git fetch downloads remote updates but does not change your current files.
  • git pull fetches and then integrates updates into your current branch.
  • git merge joins histories and may create a merge commit.
  • git rebase replays your commits on top of another base, creating new commit IDs.

For example, git fetch origin lets you inspect remote changes before integrating them. Rebase can keep a feature branch's history linear, but avoid rebasing commits that other people already depend on unless your team explicitly agrees.

git fetch origin
git log --oneline --graph --all -20
git rebase origin/main
# resolve conflicts, then:
git add path/to/resolved-file
git rebase --continue

If you are unsure, stop and inspect git status. Never start with a reset or force-push just because Git shows a conflict.

7. Resolve merge conflicts without panic

A conflict means Git could not decide which version to keep. It is a human decision, not a broken repository.

  • Read the conflict markers in the file.
  • Understand what each side was trying to do.
  • Edit the file into the correct final version; remove the markers.
  • Run tests and inspect the diff.
  • Mark it resolved with git add.
  • Continue the merge or rebase.

<<<<<<< HEAD
current branch version
=======
incoming branch version
>>>>>>> feature/other-change

Do not blindly choose “ours” or “theirs.” Both versions can contain important logic. If a generated lockfile conflicts, follow the package manager and repository conventions rather than hand-editing random lines.

8. Undo changes safely: choose the right tool

This is one of the most useful Git skills. First ask: are the changes uncommitted, committed locally, or already pushed/shared?

SituationSafer starting pointMeaning
Unstage a filegit restore --staged fileKeep edits, remove from staging
Discard edits to one filegit restore fileReplace working copy with last committed version; edits are lost
Correct the latest local commitgit commit --amendReplace the latest commit; avoid if already shared
Undo a pushed commitgit revert <sha>Create a new commit that reverses it
Inspect an old commitgit show <sha>Read it without changing files

Be careful with git reset --hard: it discards tracked working-tree and index changes. git clean -fd deletes untracked files. These commands can destroy work.

Before any risky operation:

git status
git diff
git diff --staged
git branch backup-before-recovery

A backup branch protects committed history, not every uncommitted file. For valuable uncommitted work, commit it on a temporary branch or make a separate copy first.

9. Stash work when you must switch tasks

A stash temporarily stores tracked working changes so you can switch branches without making a commit. It is handy when a teammate asks you to inspect a production bug while you are halfway through a feature.

git stash push -m "WIP profile form"
git stash list
git switch main
# handle urgent task
git switch feature/profile-form
git stash pop

pop reapplies and removes the stash if successful; apply reapplies it but keeps the stash entry. Stashes can conflict, so they are not a substitute for committing valuable work. Untracked files are not included by default; git stash push -u includes them.

10. Tags, releases, cherry-pick, and bisect

  • Tag: a label for a particular commit, often a release such as v1.4.0.
  • Cherry-pick: copy the effect of one commit onto the current branch.
  • Bisect: binary-search history to find the commit that introduced a bug.

git tag -a v1.4.0 -m "Release 1.4.0"
git push origin v1.4.0
git cherry-pick abc1234
git bisect start
git bisect bad
git bisect good v1.3.0
# test each commit Git checks
git bisect good   # or git bisect bad
git bisect reset

Use cherry-pick for a targeted fix, such as bringing a small production fix into a release branch. Use bisect when a regression appeared sometime in a known range of commits and you can reliably test whether a commit is good or bad.

11. GitHub pull requests that are easy to review

A strong PR tells reviewers why the change exists, what changed, and how it was tested. Keep the diff focused, attach screenshots for UI changes, link the issue, and call out risks or follow-up work.

A useful PR template:
- Problem: what was broken or missing?
- Change: what did you implement?
- Testing: exact tests or manual steps performed.
- Screenshots: before/after for visual changes.
- Risk / rollout: any migration, feature flag, or deployment note.

Before opening a PR:

git status
git diff origin/main...HEAD
npm test
npm run lint
git push

On GitHub, review the Files changed tab, leave comments on specific lines, resolve conversations after addressing them, and use required checks and approvals. A green check means the configured check passed; it does not prove the product is bug-free.

12. Issues, Projects, Actions, releases, and security

GitHub is more than a code host:
- Issues: track bugs, tasks, and feature requests. Write reproduction steps and expected vs actual behavior.
- Projects: organize work across issues and PRs with fields, views, and workflows.
- Actions: automate tests, linting, builds, releases, and scheduled maintenance.
- Releases: publish versioned deliverables and notes, often attached to tags.
- CODEOWNERS: request review from people responsible for certain paths.
- Branch protection / rulesets: require checks, reviews, and restrict unsafe pushes.
- Dependabot: alerts about vulnerable or outdated dependencies and can propose updates.
- Secrets: store CI credentials securely; never hardcode tokens in code or commit them in .env files.

A minimal Actions workflow might run tests for each pull request. Keep secrets limited to the jobs that need them, pin third-party actions according to your organization's security policy, and do not print tokens in logs.

```yaml name: CI on: pull_request: push: branches: [main] jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: node-version: 20 cache: npm - run: npm ci - run: npm test -- --run ```

13. Git tricks that save time

See who changed a line: git blame path/to/file. This is a starting point for understanding history, not a way to assign blame socially.

Search commit messages: git log --oneline --grep="pagination".

Search code history: git log -S"oldFunctionName" --oneline -- path/to/file.

See a file's history: git log --follow -- path/to/file.

Temporarily inspect a commit: git switch --detach <sha>; return to your branch with git switch <branch>. Do not create new work while detached unless you know how to save it to a branch.

Ignore local files: add patterns such as .env, dist/, or coverage/ to .gitignore. If a file is already tracked, adding it to .gitignore will not untrack it; use git rm --cached path/to/file and commit that change.

Use aliases: git config --global alias.lg "log --oneline --graph --decorate --all" then run git lg.

Use tab completion and shell history: these reduce typos and make repeated workflows faster. Always inspect commands copied from the internet before running them.

14. GitHub CLI: do common tasks from the terminal

The GitHub CLI (gh) is a separate tool from Git. After installing it and running gh auth login, it can create PRs, inspect issues, and check CI without opening a browser.

gh auth status
gh repo view
gh issue list
gh pr list
gh pr view
gh pr checks
gh pr create --fill
gh pr checkout 123
gh run list
gh run view

These commands depend on being inside the correct repository and being authenticated. Follow your organization's authentication rules; do not paste access tokens into chat, shell history, or source files.

15. Common real-world scenarios

I committed to the wrong branch: if the commit is local, create or switch to the correct branch at the commit so it is preserved, then return the original branch to its previous state only after verifying. The exact safe steps depend on whether the commit has been pushed.

I accidentally staged a secret: remove it from the staging area, rotate/revoke the exposed credential immediately if it was committed or pushed, and follow your organization's incident process. Deleting the file in a later commit does not erase it from Git history.

My branch is behind main: fetch first, inspect changes, then rebase or merge according to team conventions. Resolve conflicts carefully and rerun tests.

I need to undo a production change: usually use git revert to create an auditable inverse commit, then test and deploy through the normal release process.

My local changes disappeared: stop running cleanup commands. Check git status, git stash list, git reflog, IDE local history, and backups. Reflog can help recover recent commits or branch movements, but it is not a guarantee for never-committed files.

The most important habit is to run git status before and after a meaningful operation. Git is easier when you understand the state, rather than blindly copying a command.

Final takeaways

You do not need to memorize all Git commands. Learn the state model, inspect changes before committing, use focused branches and commits, and prefer reversible operations for shared history. When in doubt, pause, read `git status`, and make a backup before doing anything destructive.
