1. Why frontend system design matters

Frontend system design is the process of deciding how a web application should be structured before—or while—it is being built. It covers more than component folders. It includes data flow, routing, state ownership, API boundaries, rendering strategy, performance, accessibility, security, testing, and how the application can grow without becoming difficult to change.

Consider a dashboard that starts with three pages. A single component and a few API calls may be enough at first. Later, the product adds role-based access, filters shared across pages, real-time updates, complex forms, and multiple teams working in parallel. Without clear boundaries, components become coupled, state becomes difficult to trace, and small changes create unexpected regressions.

Design principle

The goal is not to build the most sophisticated architecture. It is to choose the simplest architecture that meets today's requirements and leaves reasonable room for tomorrow's.

2. Start with requirements, not libraries

Before choosing a router, state library, or folder structure, clarify what the product needs.

Functional requirements

  • Which pages and user flows are required?
  • Can users search, filter, sort, edit, or upload data?
  • Is authentication required? Are there different roles?
  • Which actions need optimistic updates or real-time feedback?
  • What happens when an API fails or returns no results?

Non-functional requirements

  • How quickly should useful content appear?
  • How many records can a page display?
  • Does it need mobile and keyboard accessibility?
  • Are SEO and shareable URLs important?
  • How many developers or teams will work on it?

Turn vague requirements into constraints. “The page should be fast” is not actionable. “The product list may contain 20,000 items, but the browser should render only a small visible window” points toward pagination or virtualization.

3. Sketch the high-level architecture

A typical React application can be separated into layers with clear responsibilities.

BrowserRoutes · URL · User interaction · Accessibility
↓
Page / Feature UIProductPage · SearchPanel · OrderDetails
↓
Application LogicHooks · Use cases · Validation · Policies
↓
Data / API LayerAPI client · DTO mapping · Error handling
↓
Backend services / APIs

The exact number of layers is flexible. The important part is that each layer has a reason to change. A button's styling should not need to know how authentication tokens are attached to requests. A page should not need to duplicate HTTP error parsing.

4. Organize code around features

There is no one folder structure that is right for every application. As the application grows, organizing by business feature often makes ownership clearer.

How to decide where code belongs

  • Shared UI component: reusable presentation with a stable interface, such as a button or modal.
  • Feature component: UI that makes sense mainly inside one feature, such as ProductFilters.
  • Hook: reusable stateful behavior or coordination, not simply a way to hide every line of code.
  • API module: endpoint calls, request parameters, and response handling.
  • Utility: pure transformations such as currency formatting or sorting.
  • App layer: routing, global providers, and application-wide configuration.

Do not move every two-line helper into a new folder. Abstraction has a cost. Extract code when it has a clear responsibility, is reused, or makes a complex boundary easier to test.

5. Define component boundaries

A good component should have a clear job and a reasonably small public interface.

type ProductCardProps = {
  name: string;
  price: number;
  imageUrl: string;
  onSelect: () => void;
};

export function ProductCard({
  name, price, imageUrl, onSelect,
}: ProductCardProps) {
  return (
    <article className="product-card">
      <img src={imageUrl} alt="" loading="lazy" />
      <h2>{name}</h2>
      <p>{price.toLocaleString()}</p>
      <button onClick={onSelect}>View product</button>
    </article>
  );
}

This component displays a product and reports user intent. It does not fetch data, decide access permissions, or manage the whole page's filters.

Rule of thumb

Keep decisions near the layer that owns them, and pass only the information a child needs.

Avoid both extremes: a giant page component that handles everything, and hundreds of tiny components whose names and props make simple flows harder to understand.

6. Choose state based on ownership

State should live as close as possible to the components that need it, unless it must be shared.

State typeExampleGood default
Local UI stateModal open, current tabuseState
URL stateSearch query, sort, pageURL search params / router
Server stateProducts returned by APIQuery/cache library or explicit data layer
Shared client stateActive workspace, UI preferencesContext or a state store
Form stateField values, validation errorsLocal state or form library

Do not put every value in a global store. Global state creates shared coupling and makes ownership less obvious. For server data, remember that freshness, retries, invalidation, deduplication, and stale responses are different concerns from ordinary client state.

Keep shareable filters in the URL

/products?query=keyboard&sort=price&page=2

This gives users a link they can bookmark or share. It also supports browser back/forward behavior. The URL is a good source of truth for state that should survive refreshes or be shareable.

7. Design the data-fetching flow

User changes filter
↓
URL / feature state updates
↓
Query key changes
↓
API layer sends request
↓
Loading / success / error state
↓
UI renders current result

For example, using TanStack Query:

function useProducts(query: string, page: number) {
  return useQuery({
    queryKey: ["products", { query, page }],
    queryFn: () => productsApi.list({ query, page }),
  });
}

The query key should include the inputs that change the result. Otherwise, the cache may return data for the wrong filter. Keep API calls in a dedicated module so endpoint changes do not spread through the UI.

Handle all meaningful states

  • Initial loading
  • Refetching existing data
  • Empty results
  • Request failure
  • Partial or invalid data
  • A user changing filters while a request is in flight

Do not assume every request succeeds or that an empty array is the same as a failed request.

8. Establish API and type boundaries

Backend response shapes often differ from what the UI wants to display. Keep the conversion explicit.

type ProductDto = {
  product_id: string;
  display_name: string;
  price_in_cents: number;
};

type Product = {
  id: string;
  name: string;
  price: number;
};

function toProduct(dto: ProductDto): Product {
  return {
    id: dto.product_id,
    name: dto.display_name,
    price: dto.price_in_cents / 100,
  };
}
