1. Why frontend system design matters

Frontend system design is the process of deciding how a web application should be structured before—or while—it is being built. It covers more than component folders. It includes data flow, routing, state ownership, API boundaries, rendering strategy, performance, accessibility, security, testing, and how the application can grow without becoming difficult to change.

Consider a dashboard that starts with three pages. A single component and a few API calls may be enough at first. Later, the product adds role-based access, filters shared across pages, real-time updates, complex forms, and multiple teams working in parallel. Without clear boundaries, components become coupled, state becomes difficult to trace, and small changes create unexpected regressions.

Design principle

The goal is not to build the most sophisticated architecture. It is to choose the simplest architecture that meets today's requirements and leaves reasonable room for tomorrow's.

2. Start with requirements, not libraries

Before choosing a router, state library, or folder structure, clarify what the product needs.

Functional requirements

  • Which pages and user flows are required?
  • Can users search, filter, sort, edit, or upload data?
  • Is authentication required? Are there different roles?
  • Which actions need optimistic updates or real-time feedback?
  • What happens when an API fails or returns no results?

Non-functional requirements

  • How quickly should useful content appear?
  • How many records can a page display?
  • Does it need mobile and keyboard accessibility?
  • Are SEO and shareable URLs important?
  • How many developers or teams will work on it?

Turn vague requirements into constraints. “The page should be fast” is not actionable. “The product list may contain 20,000 items, but the browser should render only a small visible window” points toward pagination or virtualization.

3. Sketch the high-level architecture

A typical React application can be separated into layers with clear responsibilities.

BrowserRoutes · URL · User interaction · Accessibility
↓
Page / Feature UIProductPage · SearchPanel · OrderDetails
↓
Application LogicHooks · Use cases · Validation · Policies
↓
Data / API LayerAPI client · DTO mapping · Error handling
↓
Backend services / APIs

The exact number of layers is flexible. The important part is that each layer has a reason to change. A button's styling should not need to know how authentication tokens are attached to requests. A page should not need to duplicate HTTP error parsing.

4. Organize code around features

There is no one folder structure that is right for every application. As the application grows, organizing by business feature often makes ownership clearer.

src/
  app/
    App.tsx
    router.tsx
    providers.tsx
  components/
    ui/
      Button/
      Modal/
      TextField/
    layout/
      AppShell/
      PageHeader/
  features/
    products/
      api/productsApi.ts
      components/ProductCard.tsx
      components/ProductFilters.tsx
      hooks/useProducts.ts
      pages/ProductsPage.tsx
      types.ts
      utils/productFormatters.ts
    orders/
      api/
      components/
      hooks/
      pages/
      types.ts
  lib/
    httpClient.ts
    logger.ts
  styles/
  test/

How to decide where code belongs

  • Shared UI component: reusable presentation with a stable interface, such as a button or modal.
  • Feature component: UI that makes sense mainly inside one feature, such as ProductFilters.
  • Hook: reusable stateful behavior or coordination, not simply a way to hide every line of code.
  • API module: endpoint calls, request parameters, and response handling.
  • Utility: pure transformations such as currency formatting or sorting.
  • App layer: routing, global providers, and application-wide configuration.

Do not move every two-line helper into a new folder. Abstraction has a cost. Extract code when it has a clear responsibility, is reused, or makes a complex boundary easier to test.

5. Define component boundaries

A good component should have a clear job and a reasonably small public interface.

type ProductCardProps = {
  name: string;
  price: number;
  imageUrl: string;
  onSelect: () => void;
};

export function ProductCard({
  name, price, imageUrl, onSelect,
}: ProductCardProps) {
  return (
    <article className="product-card">
      <img src={imageUrl} alt="" loading="lazy" />
      <h2>{name}</h2>
      <p>{price.toLocaleString()}</p>
      <button onClick={onSelect}>View product</button>
    </article>
  );
}

This component displays a product and reports user intent. It does not fetch data, decide access permissions, or manage the whole page's filters.

Rule of thumb

Keep decisions near the layer that owns them, and pass only the information a child needs.

Avoid both extremes: a giant page component that handles everything, and hundreds of tiny components whose names and props make simple flows harder to understand.

6. Choose state based on ownership

State should live as close as possible to the components that need it, unless it must be shared.

State typeExampleGood default
Local UI stateModal open, current tabuseState
URL stateSearch query, sort, pageURL search params / router
Server stateProducts returned by APIQuery/cache library or explicit data layer
Shared client stateActive workspace, UI preferencesContext or a state store
Form stateField values, validation errorsLocal state or form library

Do not put every value in a global store. Global state creates shared coupling and makes ownership less obvious. For server data, remember that freshness, retries, invalidation, deduplication, and stale responses are different concerns from ordinary client state.

Keep shareable filters in the URL

/products?query=keyboard&sort=price&page=2

This gives users a link they can bookmark or share. It also supports browser back/forward behavior. The URL is a good source of truth for state that should survive refreshes or be shareable.

7. Design the data-fetching flow

User changes filter
↓
URL / feature state updates
↓
Query key changes
↓
API layer sends request
↓
Loading / success / error state
↓
UI renders current result

For example, using TanStack Query:

function useProducts(query: string, page: number) {
  return useQuery({
    queryKey: ["products", { query, page }],
    queryFn: () => productsApi.list({ query, page }),
  });
}

The query key should include the inputs that change the result. Otherwise, the cache may return data for the wrong filter. Keep API calls in a dedicated module so endpoint changes do not spread through the UI.

Handle all meaningful states

  • Initial loading
  • Refetching existing data
  • Empty results
  • Request failure
  • Partial or invalid data
  • A user changing filters while a request is in flight

Do not assume every request succeeds or that an empty array is the same as a failed request.

8. Establish API and type boundaries

Backend response shapes often differ from what the UI wants to display. Keep the conversion explicit.

type ProductDto = {
  product_id: string;
  display_name: string;
  price_in_cents: number;
};

type Product = {
  id: string;
  name: string;
  price: number;
};

function toProduct(dto: ProductDto): Product {
  return {
    id: dto.product_id,
    name: dto.display_name,
    price: dto.price_in_cents / 100,
  };
}

This mapping prevents backend naming conventions from leaking throughout the UI. TypeScript catches many development-time mistakes, but it does not validate unknown JSON at runtime. For untrusted or externally supplied data, validate at the boundary when the risk justifies it.

9. Routing, layouts, and code splitting

/                         → Home
/products                 → Product list
/products/:productId      → Product details
/orders                   → Orders
/orders/:orderId          → Order details
/settings/profile         → Profile settings

Routes should represent meaningful destinations, not every tiny UI state. Use shared layouts for navigation and page shells. Use route-level code splitting when it reduces the amount of JavaScript needed for the initial page.

const OrdersPage = lazy(
  () => import("./features/orders/pages/OrdersPage")
);

Lazy loading is not automatically beneficial everywhere. Splitting too aggressively can create many small network requests or delay important UI. Measure the initial bundle and real user experience, then split large or infrequently used features.

10. Performance is an architectural concern

  • Load only what the route needs.
  • Use pagination or virtualization for large collections.
  • Compress and appropriately size images.
  • Cache server responses where freshness rules allow it.
  • Avoid waterfalls by starting independent requests in parallel.
  • Keep expensive calculations out of repeated render paths.
  • Measure before adding memoization.
  • Track Core Web Vitals and real-user behavior where possible.

If a page requests a profile and then waits for it before starting an independent list request, it creates an unnecessary waterfall. If requests are independent, start them concurrently.

const [profile, products] = await Promise.all([
  getProfile(),
  getProducts(),
]);

Only parallelize requests that truly do not depend on one another. Also consider loading priorities, caching, error handling, and whether the UI can progressively display useful content.

11. Accessibility and security belong in the design

Accessibility is not a final styling task. Plan semantic HTML, keyboard navigation, focus behavior, visible focus indicators, labels, error messages, and sensible heading structure as components are designed.

  • Do not treat frontend route guards as authorization; the backend must enforce permissions.
  • Avoid storing sensitive credentials in client-side code.
  • Do not render untrusted HTML without an appropriate sanitization strategy.
  • Handle authentication expiry and forbidden responses consistently.
  • Avoid leaking secrets in logs or client bundles.

The frontend can improve usability and reduce accidental access, but it cannot replace server-side security controls.

12. Testing strategy follows the boundaries

  • Unit tests: pure transformations, validation, formatters, and isolated logic.
  • Component/integration tests: a feature's visible behavior when components and data interactions work together.
  • End-to-end tests: a small number of critical journeys, such as sign-in, checkout, or creating an order.

Prefer testing observable behavior over internal implementation details. A component should not need extensive mocking of private helper functions just to test that a user can submit a form.

13. Failure handling and observability

Real applications encounter timeouts, expired sessions, unexpected responses, and third-party outages. Design these cases instead of treating them as surprises.

  • Show actionable, accessible error messages.
  • Provide retry behavior where retrying is safe.
  • Preserve user input when a request fails.
  • Avoid duplicate submissions for sensitive actions.
  • Log useful diagnostic information without exposing private data.
  • Track errors and performance by route or feature.
  • Use error boundaries to isolate rendering failures where appropriate.

A generic “Something went wrong” may be acceptable for an unexpected crash, but a failed save should ideally tell the user what happened and how to recover.

14. Scaling a team: contracts and ownership

As more developers contribute, code ownership and interfaces become as important as component design.

  • Agree on API contracts and error formats.
  • Define conventions for routing, query keys, and forms.
  • Keep feature modules from importing one another's internal implementation unnecessarily.
  • Use linting, type checking, and automated tests in CI.
  • Document unusual decisions and their trade-offs.
  • Introduce monorepos or micro frontends only when the coordination problem justifies them.

A shared component library can improve consistency, but it also needs versioning, documentation, accessibility standards, and a clear contribution process.

15. Common design mistakes

  1. Choosing tools before understanding requirements. Start with constraints and workflows.
  2. Putting everything in global state. Share only what genuinely needs shared ownership.
  3. Mixing API calls with presentation. Create a clear data boundary.
  4. Over-abstracting early. Wait for a real repeated pattern or a meaningful boundary.
  5. Ignoring loading and failure states. They are part of the product, not edge cases.
  6. Memoizing everything. Optimization has complexity and should be supported by measurement.
  7. Using frontend checks as security. Enforce authorization on the server.
  8. Creating micro frontends too early. Operational and integration costs can outweigh the benefits.

16. A practical design checklist

  • Are the core user flows and non-functional constraints clear?
  • Are routes and shareable URL state defined?
  • Does each feature have a clear ownership boundary?
  • Is server state handled differently from local UI state?
  • Are API response types and error handling centralized?
  • Are loading, empty, failure, and retry states designed?
  • Is the initial route bundle reasonable?
  • Are accessibility and security requirements included?
  • Can important behavior be tested without brittle implementation details?
  • Will the architecture remain understandable to the next developer?

Conclusion

Good frontend system design is not about having the most folders, the newest state library, or the largest architecture diagram. It is about making responsibilities clear, data flow predictable, and changes safe.

Start with requirements. Define feature and API boundaries. Put state where it belongs. Design for loading, failure, accessibility, and performance. Then evolve the architecture when real product or team constraints demand it.

The best architecture is the one that helps your team deliver the next feature without making the previous features harder to maintain.
