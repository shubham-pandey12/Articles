1. Why database design matters

A backend can have clean controllers and well-tested services but still become slow or unreliable if the database model is wrong. Poor schema choices create duplicate data, inconsistent updates, expensive queries, and risky migrations.

Database design decides what facts the system stores, how records relate, which rules must always be true, how data is read and updated, and how the model evolves safely. This article focuses on relational databases such as PostgreSQL and MySQL; syntax and features vary by database.

2. Start with entities and business rules

For a commerce application, imagine these rules: a customer can place many orders; an order belongs to one customer; an order contains many products; a product can appear in many orders; quantities must be positive; and each order item preserves the price agreed at purchase time.

1 ─────── *

* ─────── 1

OrderItem connects orders and products and stores relationship-specific data such as quantity and purchase price.

3. A practical relational schema

CREATE TABLE customers (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email VARCHAR(254) NOT NULL UNIQUE,
  name VARCHAR(100) NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE products (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  sku VARCHAR(80) NOT NULL UNIQUE,
  name VARCHAR(200) NOT NULL,
  current_price DECIMAL(12, 2) NOT NULL CHECK (current_price >= 0),
  is_active BOOLEAN NOT NULL DEFAULT TRUE
);

CREATE TABLE orders (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers(id),
  status VARCHAR(30) NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE order_items (
  order_id BIGINT NOT NULL REFERENCES orders(id),
  product_id BIGINT NOT NULL REFERENCES products(id),
  quantity INTEGER NOT NULL CHECK (quantity > 0),
  unit_price DECIMAL(12, 2) NOT NULL CHECK (unit_price >= 0),
  PRIMARY KEY (order_id, product_id)
);

This is illustrative, not a complete production schema. A real system may need currency, tax, discounts, snapshots of product descriptions, order status constraints, and more.

Why keep unit_price on the order item?

The product's current price can change. An old order should preserve the price agreed at checkout. The catalog price describes the present; the order-item price records the historical transaction. This is intentional duplication for correctness.

4. Primary keys, foreign keys, and constraints

Primary keys

A primary key uniquely identifies a row. It should be stable and not depend on a user-editable value such as an email. Numeric IDs and UUIDs are common; natural keys can also be unique constraints.

Foreign keys

A foreign key prevents a row from referring to a parent that does not exist. Choose deletion behavior deliberately:

  • RESTRICT / NO ACTION: prevent deletion while children exist, subject to database semantics.
  • CASCADE: delete dependent rows automatically.
  • SET NULL: keep the child but remove its reference, if allowed.

Cascade is powerful but can delete more data than expected. Use it only when it matches the business rule.

Constraints are executable business rules

Use NOT NULL, UNIQUE, CHECK, and foreign keys for invariants the database can enforce. Application validation improves user-facing errors, but database constraints protect against concurrent requests, scripts, background jobs, and future code paths. Read your database's semantics for nullable unique columns and check expressions.

5. One-to-one, one-to-many, and many-to-many

One-to-one

CREATE TABLE user_profiles (
  user_id BIGINT PRIMARY KEY REFERENCES users(id),
  bio TEXT,
  avatar_url TEXT
);

The primary key on user_id ensures each user has at most one profile.

One-to-many

For one customer with many orders, put the foreign key on the “many” side: orders.customer_id REFERENCES customers(id).

Many-to-many

CREATE TABLE product_categories (
  product_id BIGINT NOT NULL REFERENCES products(id),
  category_id BIGINT NOT NULL REFERENCES categories(id),
  PRIMARY KEY (product_id, category_id)
);

The composite primary key prevents duplicate relationships. If a relationship has its own properties—such as assigned_at, role, or sort_order—the junction table is a natural place to store them.

6. Normalization: reduce accidental duplication

Imagine storing customer_name, customer_email, and product_name on every order row. A customer's email change would require updating many rows; missing one creates conflicting facts. A normalized model stores customers, orders, products, and order items separately, connected by keys.

  • Update anomaly: one fact must be changed in many places.
  • Insertion anomaly: a fact cannot be stored without an unrelated fact.
  • Deletion anomaly: deleting one record accidentally removes another important fact.

Do not eliminate all duplication blindly. Snapshots, reporting tables, caches, and performance-oriented denormalization can be appropriate. Know which copy is authoritative and how other copies stay consistent.

7. Transactions and ACID

A transaction groups operations into one logical unit. If a required step fails, it can roll back so the database does not retain a half-finished result.

  • Atomicity: all operations happen, or none do.
  • Consistency: committed changes preserve constraints and invariants.
  • Isolation: concurrent transactions are controlled by the isolation level.
  • Durability: committed changes survive failures according to database guarantees and configuration.
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1 AND balance >= 100;

-- Application must verify exactly one row was updated.
UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;

This is incomplete without handling a failed debit, a missing destination account, and exceptions. Check affected-row counts and roll back on failure. Without a transaction, a crash after the debit can leave the system inconsistent.

Isolation levels trade off correctness guarantees, blocking, and retries. Transactions also do not make a workflow atomic across external systems; for payment/email/database workflows, consider idempotency, an outbox, or a saga pattern.

8. Indexes: speed up reads, add write cost

An index helps the database find rows without scanning the entire table. It can improve filtering, joins, and sorting, but uses storage and adds work to inserts, updates, and deletes.

SELECT id, status, created_at
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 20;

CREATE INDEX idx_orders_customer_created
ON orders (customer_id, created_at DESC);

The index may help because the query filters by customer and sorts by creation time. Whether the planner uses it depends on table size, data distribution, and query shape.

Composite index order matters

An index on (customer_id, created_at) is not identical to one on (created_at, customer_id). Composite B-tree indexes are generally most useful when queries constrain leading columns, though exact behavior varies. Design indexes around equality filters, ranges, joins, sort order, and pagination patterns.

Do not index every column. Too many indexes increase storage, write amplification, and migration cost. Covering indexes can avoid table lookups in some engines, but they increase index size and are not always worth it.

9. Read query plans instead of guessing

Use query-plan tools. In PostgreSQL, EXPLAIN shows a plan; EXPLAIN ANALYZE executes the query and reports observed timing and row counts.

EXPLAIN ANALYZE
SELECT id, status, created_at
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 20;

Inspect sequential vs. index scans, estimated vs. actual rows, join strategy, sorts, repeated loops, and time spent in each node. A sequential scan is not automatically bad: for a small table or a query returning much of the table, it may be cheaper than using an index.

Be careful with EXPLAIN ANALYZE.

It runs the query. Use a safe environment and be cautious with expensive statements or statements that have side effects.

10. Avoid N+1 queries

const orders = await orderRepository.findRecent();

for (const order of orders) {
  order.customer = await customerRepository.findById(order.customerId);
}

If 100 orders are returned, this can make 101 database calls. Consider joining the related table, fetching all customers in one query, using a batch loader, or selecting only needed fields. A join is not always the answer: it may duplicate result data or complicate pagination. Measure against the desired response shape.

11. Pagination: offset versus cursor

Offset pagination

SELECT id, created_at
FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 25 OFFSET 5000;

Simple and supports page numbers, but deep offsets can be expensive and concurrent inserts can shift page contents.

Cursor / keyset pagination

SELECT id, created_at
FROM orders
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 25;

This illustrates keyset pagination for descending order. The cursor uses a stable, unique ordering combination. Exact syntax and tuple comparison support vary by database. Cursor pagination is often better for feeds and large datasets; offset pagination may be enough for small admin tables. Always use deterministic ordering with a unique tie-breaker.

12. Query only what you need

SELECT id, name, current_price
FROM products
WHERE is_active = TRUE
ORDER BY name
LIMIT 50;

Avoid SELECT * in endpoints that need only a few fields. Explicit columns clarify the data contract and may reduce transfer and processing. Also avoid repeated queries in loops, batch independent lookups, limit result sizes, choose appropriate types, check connection-pool saturation, and measure before adding complexity.

13. Migrations: evolve schema safely

Use versioned migrations rather than manually changing production databases. A safer rollout often follows expand → migrate → contract:

  1. Expand: add a nullable column or compatible schema change.
  2. Deploy compatible code: support old and new representations if needed.
  3. Backfill: populate existing rows in controlled batches.
  4. Switch: make the new column authoritative after validation.
  5. Contract: remove old fields after running code no longer depends on them.

Large index creation and backfills need planning. Test on production-like data, estimate locks and disk usage, define rollback or forward-fix plans, deploy code and schema compatibly, and monitor load. A rollback is not always a true reversal after data has been transformed or discarded.

14. Soft deletes and audit history

ALTER TABLE customers
ADD COLUMN deleted_at TIMESTAMP NULL;

Soft deletion can aid recovery, but every relevant query must apply the deletion rule; uniqueness, foreign keys, storage, and privacy requirements need attention. A deleted timestamp does not explain who changed a row or why. Use an explicit audit log when the domain requires that history. Legal or privacy requirements may require physical erasure.

15. Data types and money

  • Use integer types for counts and identifiers where appropriate.
  • Use timestamps with a clear timezone policy.
  • Use DECIMAL/NUMERIC for exact decimal values such as money rather than binary floating point.
  • Use constraints for allowed ranges and states.
  • Store currency explicitly when values can span currencies.

For financial amounts, define rounding rules and currency precision in the domain. A DECIMAL(12,2) column alone does not implement tax, exchange rates, or business rounding policy.

16. Practical debugging workflow

  1. Reproduce the request with realistic parameters.
  2. Measure endpoint latency and isolate database time.
  3. Find the actual SQL queries being executed.
  4. Check query count for N+1 behavior.
  5. Run a query plan in a safe environment.
  6. Compare estimated and actual rows.
  7. Inspect indexes and filter/sort patterns.
  8. Check locks, connection pools, and concurrent load.
  9. Change one thing at a time.
  10. Re-measure latency and resource usage.

A query that is fast on ten rows may behave very differently on ten million. Test with representative data volumes.

17. Common database design mistakes

  1. Storing repeated facts without a reason.
  2. Relying only on application checks for uniqueness.
  3. Forgetting foreign keys and allowing orphaned records.
  4. Using floating point for exact money values.
  5. Adding indexes without checking query patterns.
  6. Assuming every sequential scan is bad.
  7. Running one query per item in a list.
  8. Using unstable ordering for pagination.
  9. Performing multi-step writes without a transaction.
  10. Running a large migration without estimating locks and load.
  11. Using soft delete without explicit query rules.
  12. Optimizing from intuition rather than query plans.

18. Implementation checklist

  • Entities and relationships reflect business rules.
  • Primary and foreign keys protect relationships.
  • Important invariants use appropriate constraints.
  • Many-to-many relationships use junction tables.
  • Historical snapshots are preserved where required.
  • Multi-step writes use transactions.
  • Indexes match measured filters, joins, and sort patterns.
  • Slow query plans are reviewed.
  • Queries avoid N+1 behavior and fetch needed fields only.
  • Pagination uses deterministic ordering.
  • Migrations are versioned, tested, and compatible.
  • Data types match precision and timezone requirements.
  • Soft-delete and audit requirements are explicit.
  • Performance is checked with realistic data volumes.

Conclusion

Good database design starts with business facts and invariants, not a list of columns. Relationships and constraints protect correctness; transactions protect multi-step updates; indexes and query plans help performance; and safe migrations let the system evolve.

Model the domain clearly, let the database enforce what must always be true, and use measurements to guide optimization.
